# Local Prediction Evaluation

Use the bundled scripts for unweighted, scalar regression or binary classification predictions in CSV files. They evaluate a fixed local split, compare metrics and sampling uncertainty, diagnose development errors, and construct prediction blends; task-specific data preparation, training, leakage checks, and resource checks still belong to the task adapter.

## Fit the Competition Metric

| Metric argument | Direction | Inputs and exact behavior |
| --- | --- | --- |
| `rmse` | Minimize | Finite numeric targets and predictions; square root of mean squared residual |
| `mae` | Minimize | Finite numeric targets and predictions; mean absolute residual |
| `binary_log_loss` | Minimize | Labels 0/1 and probabilities in [0, 1]; natural-log loss, clipped at epsilon and 1 minus epsilon |
| `roc_auc` | Maximize | Labels 0/1 with both classes present and finite ranking scores; ties contribute one half |

Check the contest's scorer before choosing an argument. Weighted, per-group, per-fold, multi-target, multiclass, custom aggregation, and transformed metrics require a task-specific implementation. Pooled OOF ROC-AUC is not generally equal to mean fold ROC-AUC. Log-loss epsilon defaults to `1e-15`; set `--log-loss-epsilon` to the official value when applicable, including its numerical conventions.

The default `--score-kind proxy` labels the measurement provisional. Use `--score-kind official_metric` only after verifying that the exact formula, label encoding, weights, clipping, and aggregation match the contest. The flag records that declaration; it does not check official rules or make the result a platform score.

## Establish Training and Validation Evidence

Before expensive fitting, use the [declared split check](validation-split.md) for ID overlap and, when required, group isolation or forward-time/label-availability boundaries. Save its receipt once and reuse it while dependencies match. It checks recorded partitions; match actual fitting and preprocessing to those partitions separately.

Before training, inspect the data loader as well as the modeling code. Bundled or cached features may already have been normalized using the entire dataset, imputed, target-encoded, or generated by a fitted model. Obtain raw features when possible and fit learned preprocessing only on permitted training rows within each fold. If the rules allow transductive use of held-out features, record that choice and its scope explicitly. A split made after an undocumented transform does not establish leakage-free evidence.

Give each model pipeline an identity separate from its prediction CSV hash. Save source and configuration hashes, dependency versions, dataset and split hashes, exact fitting-row IDs, transform-fitting scope, label encoding, seed protocol, and training/inference costs. For OOF predictions, retain each fold's excluded IDs/groups and fitted-pipeline lineage. These records support inspection; hashes alone do not prove correct fitting or independence.

For the [candidate archive](iteration-trace.md#retrieve-evidence-for-the-next-implementation), save the complete code/recipe directory as `--configuration`, including intended candidate arguments and feature/data identities. Store run logs and declared repetition seeds outside that directory. Different stochastic predictions from this unchanged pipeline remain separate observations of one implementation; they do not establish a new method or justify a code-change proposal. Preserve the measurements for uncertainty analysis. Prediction-only history keeps its scores and marks the missing recipe rather than counting each CSV as new code.

Start with a credible inexpensive reference, such as regularized linear models for suitable small numeric datasets; use a constant model to check the metric if useful, while assessing score gains against the credible reference. Read representative errors before committing to expensive families. When close rankings depend on a few validation cases, use the [stability protocol](score-search.md#check-whether-the-evidence-can-rank-candidates) to decide whether another measurement is more useful than another parameter variant. Keep groups/time boundaries intact and reserve final confirmation first.

Freeze the finalist pipelines and any blend recipe before confirmation. Verify that confirmation predictions use those exact pipelines; full-data retraining is a separately recorded final-artifact step. Declare how development/confirmation disagreement affects delivery before observing it. Report the aggregate scores and uncertainty even if the predeclared rule retains the reference.

For efficient iteration, reuse only intermediates whose actual dependencies match:

| Change | Reusable evidence | Work to redo |
| --- | --- | --- |
| Blend weights only | Verified member predictions and their pipeline lineage | Blend output and its evaluation; each recipe remains a trial |
| Scoring formula/evaluator only | Unchanged trained models and prediction bytes | Evaluation under the new contract and affected comparisons/diagnostics |
| Feature or training configuration | Unchanged raw data and unaffected components | Affected transforms, fitted models, predictions, and evaluations |
| Split/fold boundaries | Raw data and candidate source/configuration | Fold-dependent fitting, held-out predictions, and evidence |

A metric change that also changes the model's training objective belongs in the training-configuration row. Cached validation results never become independent confirmation by renaming them. Score comparison is usually the first filter; [decision-focused diagnostics](score-search.md#avoid-work-that-cannot-change-the-next-decision) help allocate available resources to the next decision.

## Inputs and Evaluation

Provide a local truth CSV such as `id,target` and a candidate prediction CSV such as `id,prediction`. Column names can be set with `--id-column`, `--target-column`, and `--prediction-column`. Each file must contain unique, non-empty IDs and finite numeric values. IDs are compared as exact strings, preserving leading zeros; row order can differ. Extra named columns are allowed but do not change scoring weights or aggregation. Missing/extra IDs, duplicate columns or IDs, malformed rows, and invalid metric domains fail the evaluation.

Seal the truth bytes, split ID, columns, metric, score kind, clipping parameters, and stage. Fit training and preprocessing under the task's fold protocol and save their provenance separately. Use `development` for iterative comparison and `confirmation` for the frozen shortlist on a separate split. These stage names describe intended use; they do not verify that a dataset was previously unseen.

```powershell
python <skill-dir>/scripts/evaluate_predictions.py `
  --truth <development-truth.csv> `
  --predictions <candidate-predictions.csv> `
  --metric rmse `
  --stage development `
  --split-id <frozen-split-name> `
  --output-dir <new-evaluation-directory>
```

The output directory's parent must exist. A successful run saves `predictions.csv` as the exact candidate snapshot and `result.json` with metric direction/value, validity scope, expected/completed cases, and candidate/evaluator/score-model/split/configuration hashes. It reads the truth file without copying it into the run. Keep truth bytes fixed when reusing evidence; use the saved prediction snapshot when reproducing an evaluation. Inputs are UTF-8 CSV, optionally with a BOM; the scripts use Python's standard library and do not train models or execute candidate code.

`valid: true` covers prediction format, ID coverage, finite values, and the metric domain only. The result lists training leakage, training provenance, resource limits, and competition rules as unchecked. The skill must establish those checks separately before promoting a competition entry. A failed run exits with code 2 and records a null score when a new output directory was created; an existing directory is never overwritten.

Add `--case-profile` to an individual evaluation when aligned per-sample losses will help choose the next construction. RMSE emits `squared_error`, MAE `absolute_error`, and binary log loss `binary_log_loss` with the same clipping epsilon, all minimized and keyed by the exact CSV IDs. The option leaves the aggregate metric and scoring configuration unchanged. ROC-AUC has no supported per-row decomposition and rejects this flag; ordinary AUC evaluation remains available. Archive a complete training recipe with predictions before using these profiles as parent evidence. Case wins alone do not decide whether blending helps; use the [two-parent direction diagnostic](#check-whether-a-two-parent-blend-has-a-useful-direction) where applicable.

## Batch Ready Candidates

When several prediction files already exist and share one truth/split, stage, metric, columns, clipping, and score kind, use `evaluate_prediction_batch.py` to evaluate them sequentially in one Python process. It calls the original evaluator and saves its unchanged result schema/hash, freezes one shared truth snapshot, and verifies each saved comparison input once. Do not delay useful feedback just to fill a batch; individual evaluation remains suitable when the next trial depends on the current outcome.

```powershell
python <skill-dir>/scripts/evaluate_prediction_batch.py `
  --truth <development-truth.csv> `
  --candidate baseline <baseline-predictions.csv> `
  --candidate route-a <route-a-predictions.csv> `
  --candidate route-b <route-b-predictions.csv> `
  --baseline baseline `
  --metric rmse --stage development --split-id <frozen-split-name> `
  --output-dir <new-batch-directory>
```

The output contains `truth.csv`, `batch.json`, `evaluations/<name>/result.json` with its prediction snapshot, and optional `comparisons/<name>.json` against `--baseline`. Child results work with the existing comparator, blend, error, and uncertainty tools; supply the batch's saved truth bytes to diagnostics. Default metric interpretation, column options, log-loss epsilon, and tie epsilon follow the individual tools. `--baseline` is optional and must exactly name a batch candidate; it selects the comparison reference, without promoting a winner.

Provide 1-64 candidates with distinct case-insensitive portable ASCII names; directory traversal, trailing dots, and Windows device names are rejected. Each failed candidate has a null score and its own error record; valid candidates continue. A failed baseline produces no comparisons. `partial_failure` or a fatal batch failure returns code 2; only complete success returns 0. Existing output directories are never overwritten. A fatal infrastructure failure can leave completed child artifacts; inspect their individual evidence before reuse.

Batching applies only to already constructed candidates under a shared contract. Each tested configuration still consumes its own trial slot; training provenance and hard rules remain separate checks. Use confirmation batching only for the frozen shortlist. This entry does not train, search weights, bootstrap every pair, choose a candidate, or submit an entry.

## Compare Local Scores

```powershell
python <skill-dir>/scripts/compare_prediction_results.py `
  --baseline <baseline-evaluation/result.json> `
  --candidate <candidate-evaluation/result.json> `
  --output <new-comparison.json>
```

The comparator accepts only complete successful results with matching evaluator, metric/score model, split, stage, and evaluation configuration. Keep each result beside its `predictions.csv`; it verifies the snapshot hash. It reports raw score delta, improvement oriented in the correct metric direction, and `metric_preference` as baseline/candidate/tie. `--tie-epsilon` defaults to `1e-12` and is a numerical threshold, not a statistical confidence interval. Existing comparison files are never overwritten.

The default fast path checks the saved result metadata and prediction snapshot hashes; it does not recompute scores or require the installed evaluator to match an older pair's evaluator. When resuming cached evidence or investigating a saved-score discrepancy, add `--truth <frozen-local-truth.csv>` to the comparison command. This optional audit uses the shared paired-evidence loader to verify the exact truth bytes, installed evaluator, columns/formula/parameters, ID coverage, row counts, prediction snapshots, and recomputed scores. It works on matched development or frozen confirmation pairs and returns aggregate evidence, without exploratory case/slice outputs.

A successful audit adds `score_verification` with the two result-file hashes, truth hash/path, and verification-code hash; the metric preference and tie tolerance follow the fast path. Reuse that receipt only while result, truth, prediction, evaluator, and verification dependencies still match. It remains separate from training provenance, leakage, resource compliance, and the decision to promote. A mismatch returns code 2 without falling back to unverified comparison or overwriting existing output.

If only scoring/evaluator dependencies changed, preserve eligible model/prediction artifacts and reevaluate them under the new contract before comparing; the audit does not convert old scores to a new formula. If truth/split or training dependencies changed, review the affected fitting and prediction lineage first. A changed or inconsistent cached score needs a new evaluation record, not an edit to the old result. Audit costs count as diagnostics; this option does not train a new candidate or expand the trial budget.

This preference is about the deterministic local metric. Independently check training repeatability, task hard rules, and final confirmation; a favorable CSV score alone does not prove the full model should be promoted. Compare separate confirmation results with one another, never a development result directly against a confirmation result. For metrics outside this interface, extend the task's adapter rather than substituting a supported metric and calling it official.

## Estimate Paired Sampling Uncertainty

Use `compare_prediction_uncertainty.py` when ranking fixed candidates for performance on unseen samples and the observed difference may depend on the validation sample. It loads a matched pair of complete evaluations, verifies truth and prediction bytes, recomputes recorded scores with the installed evaluator, and resamples the **same units for both candidates**. It retains the deterministic `aggregate_comparison` separately from `uncertainty`; a positive local difference can have an interval spanning zero. This is optional evidence for a decision, not a universal significance gate or a replacement score.

Choose the sampling unit, replicates, seed, confidence level, and practical improvement threshold before viewing the comparison, and freeze these for confirmation. Repeating with different seeds until an interval becomes favorable is additional selection on the same data. Use row resampling only when rows can reasonably be treated as independent exchangeable samples:

```powershell
python <skill-dir>/scripts/compare_prediction_uncertainty.py `
  --baseline <baseline-evaluation/result.json> `
  --candidate <candidate-evaluation/result.json> `
  --truth <frozen-local-truth.csv> `
  --resampling-unit row `
  --bootstrap-samples 1000 `
  --seed 0 `
  --confidence-level 0.95 `
  --minimum-improvement 0 `
  --output-dir <new-uncertainty-directory>
```

For dependent rows within patients, devices, or another defensible independent cluster, use `--resampling-unit group --groups <metadata.csv> --group-column patient`. The metadata needs the evaluated ID column and a non-empty group column, with unique IDs and exact sample coverage. Each draw selects the original number of groups with replacement and includes every selected group's rows; duplicated groups repeat their rows. Each replicate computes the **pooled row metric**, including unequal group sizes; it does not substitute an equally weighted mean of group scores. At least two units are required to compute a result, but a small number of independent units can still give an unreliable interval. Row/group bootstrap does not implement time-series block resampling or fix distribution shift; use a task-specific protocol when these assumptions do not fit. It is unnecessary for an exact deterministic objective on a fixed exhaustive test population.

The output saves `report.json`, all replicate scores/differences in `bootstrap.csv`, parent prediction snapshots, and group metadata when supplied. The report includes the empirical percentile interval for improvement (positive is better), configuration/input/estimator hashes, requested/valid/invalid replicate counts, independent unit count, Python version, and consumed row draws. `--bootstrap-samples` supports 100-10000 draws. `--max-row-draws` defaults to 2,000,000 total resampled row occurrences as a computational safety guard: expected work is checked before sampling and the actual total is checked during sampling, including invalid AUC draws. Cluster draws can exceed their expectation. Increase the guard when the machine can safely handle the work; it is not an optimization quota. These repetitions consume compute/time, without creating additional candidate versions. Existing output directories are never overwritten; failed invocations return code 2 with a reason in a new directory's report.

Immutable metric inputs are validated before sampling. The engine caches row residuals/log losses and prepares AUC ordering once; each AUC draw uses integer row multiplicities with the original tie rule. Regression retains per-draw scaling so small residuals remain measurable when an extreme row is absent. The random draws, pooled formulas and invalid-draw accounting are preserved; the compute guard remains explicit, and this computational optimization does not add statistical evidence.

ROC-AUC draws with one class have unavailable scores. The tool reports an unavailable interval unless at least 100 draws and 90% of all requested draws are valid; valid-draw intervals are conditional on having both classes. These are operational minimums, not a guarantee of coverage. It does not redraw until success or replace undefined AUC by zero. `uncertainty.status: unavailable` with top-level `status: success` means the procedure completed and reported insufficient evidence.

`evidence_preference` is `candidate_supported` when the lower interval endpoint exceeds `--minimum-improvement`, `baseline_supported` when the upper endpoint is below its negative, and `inconclusive` otherwise. The practical threshold uses the declared metric's units and defaults to zero. `fraction_above_minimum` is the fraction of valid bootstrap improvements exceeding that threshold; it is not a p-value or probability of winning. The interval concerns fixed predictions conditional on independent exchangeable units. It does not measure model training randomness, account for candidate search/multiple comparisons, correct leakage, or establish leaderboard improvement. Evaluate matched training seeds or independent splits where those uncertainties affect the next decision.

Use development evidence to choose the next experiments. For a frozen confirmation shortlist, this aggregate uncertainty comparison can run on paired confirmation evaluations under its predeclared protocol, without generating exploratory case/slice diagnoses. An inconclusive candidate may remain a promising alternative; resolve uncertainty with affordable independent evidence or report it when no useful evidence can be obtained. Keep the score, feasibility, compute cost, and confirmation evidence explicit rather than silently converting a diagnostic interval into a competition metric.

## Diagnose Development Errors

Use `analyze_prediction_errors.py` when a total score leaves the next improvement mechanism unclear, or when a candidate's gains might hide specific regressions. It requires paired complete development evaluations from the installed evaluator and the exact evaluated truth bytes. It verifies snapshot hashes, recomputes both overall scores, and rejects mismatched contracts, modified artifacts, or confirmation-stage evaluations. Older evaluator versions require reevaluation. An exploratory diagnosis consumes evaluation time/compute; it is not a new candidate unless it leads to a code/configuration variant.

```powershell
python <skill-dir>/scripts/analyze_prediction_errors.py `
  --baseline <baseline-development/result.json> `
  --candidate <candidate-development/result.json> `
  --truth <frozen-development-truth.csv> `
  --slices <development-metadata.csv> `
  --slice-column regime `
  --slice-column device `
  --output-dir <new-diagnostic-directory>
```

Omit `--slices` and all `--slice-column` options for per-sample analysis only. Metadata must contain the evaluated ID column and requested categorical columns, with unique IDs covering exactly the evaluated samples and non-empty category values. Rows can differ in order. Each column is analyzed independently, without automatic intersections or bins. Default `--max-groups 100` bounds the groups per column; choose meaningful regimes rather than slicing by a near-unique identifier. The diagnostic configuration and metadata hash are recorded separately from the frozen evaluation configuration.

Output includes `report.json`, all aligned cases in `cases.csv`, parent prediction snapshots in `baseline.csv`/`candidate.csv`, and the metadata snapshot when provided. These diagnostics include targets and belong in the competition workspace. The report preserves the aggregate metric comparison, per-group case counts/scores and objective improvements, and up to `--top-k` (default 10, maximum 100) worst candidate errors and regressions. `--error-tie-epsilon` defaults to `1e-12`; it affects case counts and regression lists, not aggregate candidate preference or statistical significance. Existing output directories are never overwritten; failures return code 2 and a reason in a new directory's `report.json`.

Add `--summary-only` when aggregate evidence, slices and representative top cases answer the current question. It still verifies and scores all evaluated rows and retains the same counts, slice statistics and top-case ordering, while saving only `report.json`. This skips full-case export and copied input snapshots, reducing diagnostic work. The summary records its output mode and references original results/truth plus optional slice metadata and hashes; retain those original prediction/evidence files for reproduction. Full export remains available when inspecting other cases is necessary. Both modes stream row records and select only the requested top cases instead of retaining an entire diagnostic row table; input validation and per-row score arrays still require memory proportional to split size.

| Metric | Per-case diagnostic | Error-share meaning |
| --- | --- | --- |
| RMSE | Absolute residual; regressions ranked by squared-error increase at a common scale | Fraction of total squared error for that candidate |
| MAE | Absolute residual | Fraction of total absolute error for that candidate |
| Binary log loss | Per-row loss using the evaluation's clipping epsilon | Fraction of total clipped log loss for that candidate |
| ROC-AUC | No independent row loss, error share, or case preference | Group AUC only when both classes are present; otherwise null with a reason |

For RMSE, `scaled_squared_error_improvement` equals the baseline squared residual minus the candidate squared residual, divided by `squared_error_scale` squared. The shared scale is the largest residual across both candidates, with zero improvements when it is zero. This ranks score-relevant regressions without squaring large numbers; the field is null for other metrics. `error_improvement` and the case-tie threshold still use absolute residual units for regression.

Case-win counts do not determine the official metric. Error shares are normalized separately for each candidate (zero when total error is zero); their changes are not marginal score improvements. Group scores are diagnostics, not new official aggregation: averaging group RMSE or AUC generally differs from the pooled metric, and group AUC omits cross-group ranking pairs. Small or repeatedly inspected slices can give unstable hypotheses. Use representative errors and task knowledge to distinguish missing signal, implementation mistakes, split mismatch, or irreducible noise; a weak slice alone does not prove a cause.

Turn a diagnostic observation into one affordable next test, such as a fold-safe feature, preprocessing correction, targeted data check, or complementary blend. A selector may use only permitted inference-time features, never per-sample truth or observed errors. Validate changes on the unchanged full development objective and independently confirm the frozen shortlist. Editing after inspecting confirmation errors makes that evidence development data; this tool deliberately keeps exploratory slicing on the development path.

### Check Whether a Two-Parent Blend Has a Useful Direction

When deciding whether to spend a trial on two compatible predictions, add `--check-blend-direction` to the error analysis command, optionally with `--summary-only`. For unweighted RMSE/MAE, `blend_direction` checks the signs of each endpoint's **inward one-sided loss derivative** along `(1-w)*baseline + w*candidate`, `0 <= w <= 1`. It neither constructs weights nor evaluates a recipe. It uses exact rational arithmetic on the parsed finite float values so cancellation, squared-error overflow/underflow, and MAE zero-residual kinks do not flip the signs. Its additional computation is optional and consumes diagnostic time; the case-tie epsilon does not change this check.

| Result | Development-only implication | Next decision |
| --- | --- | --- |
| Both inward signs negative; `strict_gain_over_best_parent_possible: true` | Some ideal interior weight beats both parents on these rows | Consider one affordable recipe; equal weights can still lose |
| Any inward sign zero or positive; `minimizing_endpoints` names that parent | That endpoint minimizes this convex segment; no strict gain over the best parent is possible | Skip weight trials whose only goal is improving this same split/metric with these two parents |
| `status: unavailable` | This check supports neither clipped binary log loss nor ROC-AUC | Use metric-specific evidence; unavailable does not reject a blend |

For RMSE the convex loss is MSE, which has the same minima. Let `r0 = baseline-target`, `r1 = candidate-target`, and `d = candidate-baseline`. The two inward derivative signs are those of `sum(r0*d)` and `-sum(r1*d)`. For MAE the baseline contribution is `sign(r0)*d` when `r0 != 0`, otherwise `abs(d)`; at the candidate use direction `-d`. A non-negative endpoint derivative of a convex loss makes that endpoint a minimum. Both negative imply a minimum strictly below both endpoints. This concerns ideal real-arithmetic blending of the parsed inputs; constructed CSVs and evaluator rounding still need separate scoring. Log-loss clipping can introduce flat boundary regions, and AUC depends on ordering, so these criteria are not transferred to them.

Case wins are neither necessary nor sufficient: with targets `[0,0]`, baseline `[1,2]` and candidate `[4,1]` each wins one case, yet no blend beats baseline RMSE. Conversely baseline `[1,1]` and candidate `[-2,2]` gives the candidate no wins, yet an interior blend can improve RMSE. The check gives no practical gain size, selected weight, training/resource validation, or independent evidence. Any chosen weight recipe remains a candidate trial, including a rejected recipe; do not hide weight selection or score sweeps as diagnostics. The criterion covers exactly two fixed parents on this declared development objective and does not establish other splits, metrics, nonlinear combinations, or ensemble gains.

## Construct and Confirm a Prediction Blend

When compatible models have evidence of useful held-out error interaction, use `blend_predictions.py` to test a convex weighted mean without retraining. If RMSE/MAE error diagnostics are needed for this decision, [check the two-parent direction](#check-whether-a-two-parent-blend-has-a-useful-direction) instead of relying on case wins alone. This is candidate construction; evaluate its output with the same frozen evaluator and compare against the best individual candidate. A weaker individual model can help a blend, while highly similar predictions can add cost without gain. Check the actual metric rather than inferring improvement from diversity alone.

Create a recipe from at least two named, complete **development** evaluations with matching metric, evaluator, split, stage, and configuration:

```powershell
python <skill-dir>/scripts/blend_predictions.py create `
  --member model-a <model-a-development/result.json> `
  --member model-b <model-b-development/result.json> `
  --weights 3 1 `
  --output-dir <new-blend-directory>
```

Weights correspond to the member order in this command. They must be finite, non-negative, and have a positive total; the tool normalizes and saves them. It reads the verified `predictions.csv` beside each result and aligns exact string IDs. It saves blended `predictions.csv`, `recipe.json`, byte-for-byte parent prediction snapshots under `parents/`, and `manifest.json` containing parent, recipe, builder, and candidate hashes. The manifest has a null score and is not an evaluation result. Custom ID/prediction columns are inherited from the development evaluations. Input/output CSVs use the same scalar interface as the evaluator.

Count every tested weight recipe as a candidate trial, including recipes rejected after cached-prediction evaluation. Propose a fixed blend from development error complementarity and evaluate it, keeping the confirmation reserve; do not automatically sweep weights. A dedicated tuning campaign requires an explicit user request under `SKILL.md`. The tool does not optimize weights, stack models, calibrate outputs or compute a score. For ROC-AUC it blends raw ranking scores, whose scales may differ; it does not silently rank-normalize them. For log loss, blending probabilities keeps the convex result in [0, 1]. Do not average incompatible target encodings, units or prediction interpretations.

Once selected, apply the **same recipe** to confirmation or final-test predictions using the same named model pipelines:

```powershell
python <skill-dir>/scripts/blend_predictions.py apply `
  --recipe <selected-blend-directory/recipe.json> `
  --member model-b <model-b-confirmation.csv> `
  --member model-a <model-a-confirmation.csv> `
  --output-dir <new-confirmation-blend-directory>
```

Member order may change here: weights map by exact name. Choose distinct ASCII member names without case-only differences or Windows device names so parent snapshots remain portable. All recipe members must be present, including zero-weight members, with identical sample coverage within this invocation; new sample IDs can differ from the development IDs. The tool validates the recipe content hash and copies the unchanged recipe into the new output. `apply` requires no labels and has no weight override. Evaluate confirmation predictions with `--stage confirmation` on the sealed independent truth; compare with separately evaluated individual confirmation predictions. Changing weights after looking at confirmation outcomes turns that evidence into development data and requires fresh confirmation for an unbiased claim.

Member names and hashes identify artifacts, not model semantics. Record the exact model/preprocessing configurations behind each name and verify that confirmation/test predictions come from the selected pipelines. Parent CSVs must have valid OOF or held-out provenance; blending cannot repair leakage. Measure combined model inference time/memory and permitted dependencies under the task rules. Recipe hashes detect accidental changes; they are not signatures or proof of provenance. Existing output directories are never overwritten; a failed run returns code 2 with a null score in a new directory's manifest. A failed or incomplete construction cannot be used as an evaluated candidate.
