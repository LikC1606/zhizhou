# Recover from a Score Plateau

Read this when comparable refinements have weak returns, local metrics conflict with platform feedback, or verification dominates useful implementation. Use existing evidence and notes; this is a decision boundary, not a new report or mandatory diagnostic campaign.

First distinguish missing candidate ideas from uncertainty about existing candidates. More repetitions can clarify a ranking; they cannot propose a missing representation. If recent work only adjusts the incumbent's windows, caches or cleanup, revisit the [task formulation and strong-solution strategy](strategy-design.md) before scheduling more of the same comparisons. A coherent task-derived alternative can justify a complete prototype without a newly measured hotspot or guaranteed gain.

## Establish What Can Actually Improve

Separate the contest objective from local proxies, hard feasibility from ranking, and a runtime hotspot from score headroom. For thresholded or saturated score terms, determine the relevant operating range when evidence permits: faster execution may buy feasibility or more experiments without buying contest points. If thresholds, case weights or hidden terms are unknown, retain raw components and tradeoff candidates; state what could reverse the choice. Check proxy ordering against available platform feedback without fitting away contradictory outcomes or assuming a submission authorization.

Use an applicable bound, stronger reference or independently scored feasible solution when it can change the next implementation. Distinguish unavoidable loss, a relaxation gap, and a demonstrated gap to a feasible better solution. A loose bound is neither a witness nor a promised gain; a small-case optimum is not a large-case algorithm. Reuse existing oracle results before solving more cases. When evidence is missing, choose a targeted diagnostic or complete novel prototype that can distinguish explanations. A new route need not promise a large gain before it can be tested.

Ask what capability would reach the better solution: a different representation, coupled decision, usable data signal or complete training/policy change. Low scores, time spent in a function, or an unexplained residual alone do not identify that capability. For sequential tasks, test the whole relevant horizon; an improvement in one update may damage later states.

For LLM/agent entries, separate missing correct generations, correct samples lost by the selector, parsing/timeouts, and failures after a valid intermediate action. These suggest different layers in [the mechanism guide](llm-agent-competitions.md#choose-the-layer-from-evidence). [Vote replay](inference-vote-replay.md) can expose selection gaps and redundant sample slots within a recorded pool; that pool's retrospective coverage is neither an executable score nor evidence of unsampled capability. A new generation or interaction policy still needs a complete executed comparison.

## Test a Different Mechanism

Compare the next refinement with a complete alternative aimed at the remaining limitation or structural opportunity. Choose the parent from matched historical best versions and relevant simpler baselines, not automatically the latest or largest implementation. Allow a standalone prototype behind the same task interface instead of inheriting every old heuristic, cache and fallback. When learning from a stronger solution, reconstruct the construction, cost model and maintenance dependencies before transplanting a module. Implement the coupled components needed to test the new representation; keep the incumbent available.

State the concrete capability and expected observable difference. A renamed route, wider local window, another cleanup pass or cache remains a refinement unless it changes the limiting mechanism. When component interactions matter to the next choice, use a selective ablation or replacement comparison; retain, replace or delete layers according to their measured contribution. Code length alone cannot establish quality or overhead.

A retired route returns control to the next supported mechanism or consequential diagnostic. It does not automatically trigger packaging or end the task. If no concrete successor is apparent, identify the missing evidence and revisit the formulation, using a fresh context in an unattended campaign. Stop for a user request, an applicable hard/resource constraint, an observed unresolved blocker or verified task completion. An exhausted idea list calls for strategy review; arbitrary edits and repeated requests to renew a round do not resolve it.

## Match Verification to the Decision

| Decision being made | Evidence to collect now |
| --- | --- |
| Does the mechanism work? | Immutable runnable prototype, interface/hard-rule checks, and the smallest development experiment exposing the predicted behavior |
| Is the candidate worth further investment or development promotion? | Matched full-fidelity development comparison against the incumbent, with relevant objective components and resource costs |
| Which frozen finalist should be delivered? | Independent confirmation under a declared selection rule and applicable validity/resource checks |
| Is the delivered artifact correct? | Exact package bytes, build/run and required submission-format checks |

A subset or reduced-fidelity test is diagnostic unless its screening relation has been justified; a short-horizon result cannot establish a full-horizon winner. Keep development results and snapshots for alternatives without treating each as a delivery finalist. Run independent confirmation when it can change actual selection or the user requests a separately validated alternative, rather than automatically for every positive proxy delta. Build a package at the selected delivery boundary, or earlier only when needed for execution/interface validation or explicitly requested. Hard rules and correctness still apply during development; final required checks are not waived.

Reuse valid deterministic results while their dependencies match. Changing source, data or evaluation invalidates affected evidence; a disturbance confined to timing does not automatically invalidate score/output checks. Record which result is still usable and which needs measurement, without silently making an incompatible result eligible for a comparator.

## Make Timing Interpretable

Before a consequential timing comparison, check for competing evaluation work and verify the measurement boundary and machine state. Prefer serial paired/interleaved comparisons on stable, comparable resources. Keep CPU time, wall time and operation counts/cycles separate; CPU time can also change with core speed, frequency and contention. Affinity or selecting a currently idle core alone does not certify comparability.

When timing is disturbed or incumbent and candidate both show unexpected slowdowns, mark affected timing unresolved, preserve raw measurements and repeat only the necessary resource comparison under controlled conditions. Do not take the fastest run, treat shared overload as an algorithm defect, or infer official time-limit compliance from local hardware. Do not interrupt another user's job without authorization. Enforce an actual hard limit once its boundary and applicable evidence are established; a frozen delivery rule cannot be relaxed after results are seen.
