# 项目文档与周报写作

让未参与日常开发的人读懂项目在做什么、已经做到哪里、接下来优先解决什么。
这些是用户的默认写作约定；本次请求另有明确要求时，以本次要求为准。
本 Skill 负责内容与组织，不代替飞书文档操作工具，也不自动授权外部写入。

## 先确定事实和文档用途

- 读取目标文档及相关上下文，确认本次要改的是项目介绍、研究方案还是周报。
- 用户要求结合最新代码时，核对相关提交、实际实现和已有验证，不只根据 README 或提交标题下结论。
- 区分主分支已合并、其他分支已提交、工作区未提交、已部署和未来计划；已合并不等于已部署。
- 代码存在不等于效果已验证；没有运行证据，就不要写成效果提升或验证通过。
- 周报中的“已完成”只收录对应时间段内有证据的工作，不把全部存量功能写成本周成果。
- 工作区中的进展可以记录，但要标明“开发中”或“待验证”，不要混入已交付能力。
- 论文观点用于提出优化方向，不能当作当前系统已经实现的能力；需要写结论时核对原文。
- 只检查支撑本次更新所需的代码和资料，不把全面审计当作写作前置条件。

## 写给人看

- 用自然、直接的中文，先说实际变化和作用，必要时再补技术细节。
- 主文不堆文件路径、commit hash、类名、缩写或命令；证据放在相关引用或简短来源说明里。
- 保留读者确实需要的技术名称，首次出现的陌生术语用一句短话解释。
- 用具体动作和结果替代“赋能、闭环、抓手、生态、全链路”等空话，删掉没有事实支撑的评价。
- 不把目录整理、文档更新或读了论文包装成系统能力提升；确需记录时说明实际产出。
- 不为了显得完整而增加层级、模块、重复总结或没有新信息的小节。

## 各类文档各司其职

### 项目介绍

- 开头有一句有分量的工作定位：讲清项目要解决的核心问题、长期目标和实际价值。
- 定位不能停在“做一个工具”或某项零散功能，也不能用宏大口号冒充定位。
- 将长期目标写成目标，不暗示所有目标都已实现。
- 首页保留稳定的定位、当前能力概览和必要导航；本周已完成与下周计划放在周报专栏。
- 已有周报时，不在首页再复制一份“本周已完成”。

### 研究方案与长期计划

- 先说明当前系统哪里还不够，再写要往哪个方向改、改好后能带来什么。
- 围绕少数长期目标组织近期行动，让读者看出本周工作如何推进长期目标。
- 从论文吸收方法时，落到当前系统的真实缺口；不要把论文摘要直接当成计划。
- 同一方向的代码、实验和界面工作尽量合并表述，不拆成一长串实现任务。

### 工作周报

- 每期标明实际日期范围；新一期放在最前面，旧一期保留在后面。
- 同一期先写“本周已完成”，再写“下周计划”。
- 已完成写“做成了什么、现在能做什么”，合并同一成果下的零散提交。
- 有必要交代的限制，直接写在相关成果后，不另建繁琐的状态栏目。
- 更新当前期时修改对应内容；发布新一期时才新增日期小节，避免重复记录。

## 计划的约束

- 默认按 1.、2.、3.、4. 编号写 4 条；事项少时可减，不为凑数增加任务。
- 通常控制在 5 条以内；确有需要可扩展，但每次最多 10 条。
- 每条只写一句，正文不超过 100 字，序号不计；一个长任务不能拆成多句绕过限制。
- 每条围绕一个主要方向，写出对当前系统的改进及预期结果；有必要时简短交代现有不足。
- 优先选择影响后续研究能力、可靠性、成本或使用体验的方向，按重要程度排序。
- 计划是目标，不是开发流水账；文件修改、接口拆分、参数调整等细节留在内部任务中。
- 用自然语句连接问题、动作和结果，不强制套“问题、方案、收益”等模板。
- 缺少数据时不编造百分比、工期或性能承诺；需要验证的效果明确写成验证目标。

示例，仅在符合实际情况时采用：

> 把每次证明中有用的引理和失败原因保存下来，让后续任务能接着用，减少重复尝试。

具体优化方向每次都要根据当前代码重新判断，不把示例或上次待办当作永久缺口。

## 长度与目录导航

- 核心文档、每个子文档和每个模块都不超过 200 行；这是上限，不是需要写满的目标。
- 本地 Markdown 按正文物理行检查；飞书按读者可见的逻辑段落和列表项检查，不按 XML 或 API 响应行数统计。
- 不用超长段落、表格或折叠块规避长度要求；优先合并重复信息，再考虑拆分。
- 拆分按读者用途进行，例如项目介绍、研究方案、周报；能在一篇内讲清楚就不继续拆。
- 使用真正的标题层级，让读者能在文档目录栏直接跳到相应小节。
- 跨文档导航优先沿用已有 Wiki 目录和节点关系，必要时使用原生文档引用。
- 普通“点击查看”链接可以补充来源，但不能替代用户要求的目录导航。
- 新增子文档时让它进入相应目录，并保留必要的上下文引用，避免留下孤立链接。
- 周报接近长度上限时，把较早记录放入按时间组织的归档，当前页保留最新内容和归档入口。

## 更新飞书时

- 实际读取或编辑正文时配合可用的 `lark-doc` Skill；只有需要调整知识库目录时才使用 `lark-wiki`。
- 普通本地起草不要求连接飞书；收到更新文档的请求后，在该请求授权范围内直接完成。
- 编辑前读取最新正文、revision 和相关 block，确定目标段落及已有导航和资源。
- 在原文上做局部增量更新，不使用整篇 overwrite；保留已有目录、引用、链接、白板和附件块。
- 发生版本冲突时重新读取，再基于新版本修改；写入结果不确定时先回读，确认后再决定是否重试。
- 写入后回读，确认正文、日期顺序、标题层级、计划长度和目录关系正确，旧记录及资源仍在。
- 只有实际回读成功才报告已更新；失败时说明已完成的草稿和具体未完成项。

## 交付前检查

- 陌生读者能否看懂定位、当前进展和下一步，而不需要先读代码？
- 已完成、开发中、待验证和长期目标是否有清楚的事实边界？
- 首页是否避免重复周报，周报是否先成果后计划、按时间倒序？
- 计划是否少而宽、每条不超过 100 字，并明确指向当前系统的优化？
- 每篇及每块是否不超过 200 行，目录能否跳转，历史与资源是否保留？
